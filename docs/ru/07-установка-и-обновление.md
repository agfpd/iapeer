# 07 — Установка и обновление

**Русский** · [English](../07-install-and-update.md)

Установка — два шага: разложить ядро и подготовить хост. Демон поднимать вручную не нужно — это делает онбординг. Ниже — оба шага, плюс обновление ядра и откат.

## Что нужно заранее

- **macOS.** Процессами управляет launchd — другой платформы пока нет.
- **[bun](https://bun.sh)** на `PATH`. Ядро исполняется через bun; скомпилированного JS в пакете нет.
- **`~/.local/bin` на `PATH`.** Сюда ставится бинарь `iapeer`. Нет в `PATH` — команда не найдётся после установки.
- **Хотя бы один агентский рантайм** — Claude Code или Codex CLI. Без него `iapeer create` и `iapeer init` откажут с явной ошибкой.

## Шаг 1. Установите ядро

```bash
npx @agfpd/iapeer
```

Запуск без аргументов выполняет установку. Она делает ровно три вещи:

1. **Раскладка.** Создаёт `~/.iapeer/` со всеми каталогами: реестр, состояние, логи, кеш, пространства рантаймов.
2. **Бинарь.** Собирает `iapeer` и атомарно кладёт в `~/.local/bin/iapeer`. Прежняя версия остаётся рядом как `iapeer.prev` — резерв для отката. Атомарность важна: между старой и новой версией нет момента, когда по пути лежит пустышка.
3. **Плист демона.** Пишет `~/Library/LaunchAgents/com.agfpd.iapeer.plist`, но **не загружает** его. Загрузку берёт на себя `iapeer onboard` (шаг 2): на работающем хосте демон уже может крутиться, и миграция на новый бинарь — осознанное действие, а не побочный эффект установки.

При установке однократно создаётся локальная подпись бинаря (для разрешений macOS). Подпись стабильна и переживает обновления.

Установка идемпотентна — повторный запуск безопасен.

Та же операция доступна как `iapeer install`, если бинарь уже стоит. Но самый первый раз — всегда через `npx` или из исходников: скомпилированный бинарь не умеет пересобирать сам себя.

## Шаг 2. Подготовьте хост

```bash
iapeer onboard
```

`onboard` готовит хост к появлению агентов. Первым делом он **поднимает демон** — загружает плист в launchd, дальше launchd держит демон сам, поднимая его заново при падении и перезагрузке. Отдельная команда `launchctl` для этого не нужна. Затем onboard регистрирует marketplace расширений в Claude и Codex, разворачивает планировщик (`notifier`), создаёт пир-человека в Telegram и ставит провайдера памяти. Старт демона идёт всегда; остальные шаги включены по умолчанию и отключаются флагами (`--no-notifier`, `--no-telegram`, `--no-memory`).

Проверьте, что демон жив и хост готов:

```bash
iapeer status
```

Вы увидите версию ядра, здоровье демона и состояние слота памяти. Код возврата ненулевой, если демон нездоров, — это удобно для скриптов-проверок.

Разбор каждого шага onboard — в [02 — Быстрый старт](02-быстрый-старт.md); рантаймы и память подробно — в [09](09-рантаймы.md) и [11](11-расширения-и-память.md).

## Диалоги первого запуска на чистой машине

На свежем macOS-хосте первый цикл install → onboard → запуск пира выводит несколько диалогов. Собственные first-run-модалки агент-рантаймов iapeer авто-снимает при поднятии пира; **три** пункта — на тебе.

**Авто-снимается (iapeer отвечает на boot пира — от тебя ничего):**

- **Claude** — theme-picker («Choose the text style»), folder-trust, импорт внешнего CLAUDE.md, dev-channels. Лончер iapeer принимает дефолт (голый Enter) на каждом.
- **Codex** — folder-trust («Do you trust the contents of this directory») пред-доверяется при создании пира и авто-принимается на boot; self-update-оффер отключён (`check_for_update_on_startup = false`) и авто-отклоняется; hooks-review авто-доверяется.
- Per-action permission/approval-промпты подавлены флагами рантайма, которые передаёт лончер (`--dangerously-skip-permissions` у Claude, `--dangerously-bypass-approvals-and-sandbox` у Codex). Отдельного экрана «accept dangerous permissions» нет.

**Три пункта на тебе (автоматизировать нельзя):**

1. **Залогинься в рантаймы — ДО onboard.** Войди в Claude Code и Codex заранее. Их экран логина — браузерный OAuth, который headless-пир не пройдёт, поэтому iapeer НАМЕРЕННО его не авто-отвечает; установленный, но не залогиненный рантайм роняет первый wake пира громко. `iapeer onboard` предупреждает, если найдёт неаутентифицированный рантайм.
2. **Пароль логин-связки — один раз, при install.** Install подписывает бинарь стабильной локальной идентичностью, чтобы Full Disk Access пережил обновления; macOS один раз спросит пароль логин-связки при создании этой идентичности. Это ожидаемо (инсталлер анонсирует). При отказе бинарь всё равно работает — просто TCC-промпты будут повторяться на апдейтах.
3. **Full Disk Access — ручной грант, без промпта.** macOS TCC нельзя выставить ни флагом, ни env, ни скриптом. Без него пир, читающий/пишущий TCC-защищённый путь (iCloud Obsidian vault, Desktop, Documents, Downloads), тихо падает с EPERM — без промпта, без зависания. Выдай в **System Settings → Privacy & Security → Full Disk Access** (`~/.iapeer` сам под `$HOME` и ничего не требует); onboard напомнит.

Gatekeeper не гейтит локально собранный CLI, запускаемый из терминала (нет quarantine-атрибута). Проверено живьём: авто-снятие claude theme-picker и codex folder-trust / update на чистом первом запуске (clean-install владельца + изолированный codex first-boot тест).

## Обновление

```bash
iapeer update                   # каскад: обновить ВЕСЬ стек — ядро + рантаймы + память
iapeer update --foundation-only # обновить только ядро
iapeer update 0.2.80            # запинить ЯДРО на конкретную версию (только ядро)
iapeer update --force           # переустановить, даже если версия уже стоит
```

Голый `iapeer update` обновляет **весь хостовый стек** одной командой — ядро (фундамент), каждый установленный рантайм и провайдер памяти, — чтобы «обновлено» значило всю машину, а не только ядро. Ядро идёт первым; рантаймы и память следуют, только если ядро поднялось здоровым.

**1. Ядро (фундамент)** — и оно ПРЕРЫВАЕТ каскад при жёсткой ошибке (не обновлять рантаймы на сломанное ядро):

1. Узнаёт нужную версию из npm. Если установленная уже совпадает и нет `--force` — ничего не делает.
2. Скачивает и собирает новый бинарь через `npm pack`, а не `npx` (бинарь не пересобирает себя сам).
3. Перезапускает демон на новый бинарь.
4. Перезапускает launchd-джобы инфраструктуры, которыми владеет ядро (`com.iapeer.*` — роутеры `timer`, `watcher`, Telegram), переводя их на заменённый бинарь. Перезапускаются именно ДЖОБЫ, а не пакетный код рантаймов — это следующий шаг. Если демон на шаге 3 не поднялся, шаг пропускается.
5. Проверяет, что демон поднялся здоровым, — пробой, а не кодом возврата команды перезапуска: подключается к сокету демона и считает здоровым, только когда тот принимает соединение **дважды подряд** (одиночная проба прошла бы и у демона, который привязал сокет и тут же упал). На проверку 15 секунд; при провале команда говорит и советует откатиться.

**2. Рантаймы** — каждый установленный рантайм-пакет (telegram-runtime, notifier-runtime) проходит version-gate, переустановку, ре-провижн, и его пиры перезапускаются (через обычный stop/start — флот persistent-peer отклоняется, не форсится).

**3. Провайдер памяти** — если слот занят, запускается его собственный update-verb (провайдер владеет своим обновлением, версией слота и перезапуском memory-демона).

Рантаймы и память — **best-effort**: ошибка компонента сообщается, остальные всё равно отрабатывают; код возврата ненулевой, если что-то упало. Агентские пиры (Claude/Codex) подхватывают новую доктрину ядра лениво на следующем пробуждении.

`iapeer update --foundation-only` делает только шаг 1 (узкий случай). Запиненный `iapeer update <версия>` — **только ядро** by design: пин версии специфичен для ядра (откат глубже одного шага или фиксация проверенной версии).

> **Обновление с версии до каскада (< 0.4.2).** Каскад исполняет *установленный* бинарь, поэтому самый первый `iapeer update` со старой версии работает по СТАРОЙ (foundation-only) логике: он поднимает ядро до каскад-способного бинаря, но рантаймы + память пока не каскадит. Запусти `iapeer update` ещё раз — теперь новый бинарь докаскадит остальное. Это разовый bootstrap; начиная с 0.4.2 — одна команда. (Свежая установка сразу ставит каскад-способный бинарь, поэтому двойной прогон ей не нужен.)

## Откат

```bash
iapeer rollback
```

Восстанавливает предыдущий бинарь (тот самый `iapeer.prev`), перезапускает демон на него и проверяет здоровье. Откат идёт **на один уровень назад** — хранится одна предыдущая версия. Это локальное «отменить последнее обновление», пока в npm выкладывают исправленную версию. Если нужно встать на версию глубже — `iapeer update <версия>`.

## Если демон не поднялся после обновления

Признак — `iapeer status` показывает нездоровый демон, или `update` завершился с предупреждением. Порядок действий:

```bash
iapeer rollback                         # вернуться на прежний бинарь
# если демон всё ещё лежит — поднять вручную:
launchctl bootstrap gui/$(id -u) ~/Library/LaunchAgents/com.agfpd.iapeer.plist
iapeer status                            # убедиться, что ожил
```
